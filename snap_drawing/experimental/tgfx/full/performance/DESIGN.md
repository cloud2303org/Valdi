# Managed bitmap render benchmark

This directory is source only. Its owner changes only `module/**`,
`compile.mts`, and this document. The parent owns compilation, generated output,
native runtimes, host integration, Android/iOS builds and devices. The frozen
`full/app` is an input fixture source and is not modified.

The report scope is **managed bitmap API throughput; not screen FPS or
GPU-vs-GPU**. The metric name is **GPU-synchronized render/readback throughput**:
`rasterInto(bitmap, true)` is the completion gate, including GPU completion and
readback where the implementation uses a GPU. Actual W source matters: the Skia
`BitmapGraphicsContext` uses `SkSurfaces::WrapPixels` / raster, whereas the TGFX
branch of `RasterContext::rasterNonDelta` calls `flushWithResult()`. These results
compare those managed APIs. They cannot establish equivalent GPU workloads,
display cadence, dropped frames, or energy usage. A parent-owned GPU fixture and
onscreen benchmark are separate measurements.

## Compile once, share exact bytes

The parent runs the installed main Node tools against the explicit experimental
source root W. Nothing in this implementation was compiled, built or launched by
the source agent. There are no new dependencies, fake drawing implementations,
native source changes or backend-specific TS branches.

```sh
W=/Users/cloud/.config/superpowers/worktrees/Valdi-node-only/tgfx-prototype-20261104
TOOLS=/Users/cloud/project/ValdiNativeRoutes/tools/valdi-rolldown
PERF="$W/snap_drawing/experimental/tgfx/full/performance"
# OUT must not already exist; choose a fresh name for each attempt.
OUT="$PERF/.local/release-001"
"$TOOLS/node_modules/.bin/tsx" "$PERF/compile.mts" \
  --tools "$TOOLS" \
  --source-root "$W" \
  --source-revision "$(git -C "$W" rev-parse HEAD)" \
  --out "$OUT"
```

The script calls the real `compileNodeModule` with module `render_benchmark`,
iOS prefix `RenderBenchmark`, mode `release` and W's `drawing` dependency. It
then calls the real `compileRuntimeModule` for W's drawing wrappers with
`compilationMode: js_bytecode` and a release asset output. It verifies the Valdi
wrapper magic, Hermes magic and pinned HBC version of every `.js` archive entry.
It does not export or bind a native runtime.

The intended output layout, checked by the script where applicable, is:

```text
OUT/
  compile-inputs.json
  compile-complete.json
  module/src/Fixtures.ts                  # generated bytes + compile provenance
  module/res/                            # unchanged PNG/font input bytes
  package/modules/
    render_benchmark.valdimodule
    drawing.valdimodule
  generated/
    android/render_benchmark.kt
    ios/RenderBenchmark/...
    ios/RenderBenchmarkTypes/...
    resources/{android,ios,ts}/...
    render_benchmark.valdimodule
    render_benchmark.map.json
    build.json
  resources/
    android/...                          # use emitted drawables + keep rules
    ios/...                              # use emitted module bundle
    ts/res.ts
    licenses/Montserrat-LICENSE.txt
  tmp/
```

`compile-complete.json` exists only after both archives and generated Context
checks pass. Inspect the actual generated files before compiling either host.
The generated archive and the copy in `package/modules` are the same bytes.
Package both archives, emitted platform resources and font license. Merely
copying the TS source or module archive without native image resources omits
the resource catalog's PNG dependency.

Compile once and copy the exact same `package/modules` archives to the Skia and
TGFX hosts on both platforms. Preserve the corresponding platform resources.
Record SHA-256 of the actual installed/bundled archives and compare with
`archiveHashes` in `compile-complete.json`; also compare each `.js` entry hash
from `archiveEntries` if archives are repacked. A new compile is not presumed
byte-identical. The runtime must match the pinned Hermes version. The parent's
native runtime exports must already include the drawing native factories; this
script only supplies their JS wrappers.

The input receipt records module/drawing/tool/contract/fixture SHA-256 values.
The revision is explicitly caller supplied and does not claim a clean checkout.
The script checks recorded input bytes again before writing the completion
receipt. No backend is inferred from compiler flags, a filename or the source
directory: `backend` in the compile receipt is null, and runtime binding remains
`unbound`. Native runtime identity, archive SHA, build flags and linked backend
belong in a separate host envelope around the original report string. Never
rewrite module provenance to make a Skia copy claim TGFX or vice versa.

## Native host contract

Root path: `render_benchmark/src/Benchmark`

Exported root class: `BenchmarkApp`

View model: `BenchmarkViewModel` (empty generated model)

Context, deliberately identical on Android and iOS:

```ts
export interface BenchmarkContext {
  report: (event: string) => void;
  nowMs: () => number;
}
```

Expected generated Kotlin package is `com.snap.modules.render_benchmark`, with
`BenchmarkApp`, `BenchmarkViewModel`, `BenchmarkContext`. Expected ObjC models
have prefix `RenderBenchmark`, including `RenderBenchmarkBenchmarkContext`;
the context initializer is expected to start with `initWithReport:` and include
`nowMs:`. The script checks these emitted identifiers, but the parent should use
the actual generated signatures rather than copying handwritten bindings.

`report` receives one JSON string per event. Preserve it in the host log or
result file, adding the actual backend/platform/build/device/installed-module
identity separately. Do not log every iteration. Avoid blocking logging, UI
updates or other host work while a measured scene is running.

`nowMs` must synchronously return **native monotonic milliseconds** as a double,
with enough resolution for individual render operations. For example Android
can use `SystemClock.elapsedRealtimeNanos() / 1_000_000.0`; iOS can use
`clock_gettime(CLOCK_MONOTONIC, ...)` converted to milliseconds. The epoch is
irrelevant. Invoke it directly on the JS calling thread; it must not block on
the UI thread. `Date.now()` and wall clocks do not satisfy this contract. The JS
validates finite, nondecreasing clock readings and positive total durations;
the host is responsible for actually supplying a monotonic source.

The host may sample process CPU, such as `getrusage`, in the `started` and
`finished` callback boundaries. Such a delta covers the **whole run**, including
setup, warmups, canary scans, JS/native callback work and scene reports. Keep it
in the host envelope, separate from the per-iteration wall durations. It is not
GPU time, per-scene CPU time, or power. A host watchdog should mark a missing
terminal report, destroyed component or stalled draw as an incomplete run.
The module never races a frame-producing draw against a timeout, so a late frame
cannot be dropped without disposal. Setup waits have a 30-second watchdog.

## Workloads and timing

Ordered suite IDs are fixed:

1. `cached-vector`: 64 colored rectangle nodes in 64 clip nodes, positioned as an
   8-by-8 grid, with per-node translation, rotation and opacity.
2. `shaped-text`: 12 labels with Latin ligature/kerning pairs, accented text and
   numbers, using the catalog's real Montserrat-Regular.ttf.
3. `image-svg`: four image rows, each with a PNG and SVG. PNG rows alternate
   unchanged byte assets and `res.pattern`; all SVGs use original fixture bytes.
4. `lottie`: the real integration `animation.json`, looping with `advanceRate=1`.
   Its native animation changes each iteration via `processFrame(16)`. First
   and last measured output hashes must differ.

Every scene is a detached actual `IManagedContext`, 360 by 640, async draw path,
delta rasterization disabled. Render, initial layout, asset loading, idle drain,
and settled layout occur before warmup. Then one RGBA8888 premultiplied bitmap,
with rowBytes = 360*4, is allocated and reused for all 330 iterations of that
scene. All scenes use a white background. The first three are explicitly cached
static trees; repeated draws intentionally test their cached state rather than
rebuild/shaping throughput. Lottie exercises native animation state updates.
No JS tree render or explicit layout occurs inside an iteration.

Each scene has **30 warmup and 300 measured iterations**. Native animation time
is initialized with `processFrame(0)` then advances 16ms each iteration, including
warmups. The animation step is synthetic and does not prescribe wall time.
First/last sample indices across the 330 iterations are 30 and 329 (zero based).

The per-iteration wall interval is:

```text
t0 = nowMs()
processFrame(16)
t1 = nowMs()
frame = await managed.draw()
t2 = nowMs()
frame.rasterInto(stableBitmap, true)
t3 = nowMs()
frame.dispose()                           # finally, outside interval
```

`durationsMs` stores t3-t0; phase arrays store t1-t0, t2-t1, t3-t2.
These include bridge, scheduling and clock callback overhead. `drawMs` includes
the asynchronous main-thread dispatch and JS continuation; it is not native
CPU-only drawing time. `rasterMs` includes the synchronous raster and readback
gate. Phase sums equal total for that iteration, apart from floating precision.
Frame disposal, array recording, hashes, pixel scans and serialization are
outside the interval. The complete detached workload is not frame paced.
There is no PNG encode, base64, image export or JS pixel copy in the timed path.

The setup `preparation` fields are `renderMs`, `initialLayoutMs`, `preloadMs`,
`settledLayoutMs`. They measure the setup intervals through the same clock.
`preloadMs` includes both idle drains. These one-off setup measurements are not
included in `durationsMs` or its throughput summary.

Fixture inputs are read from W, byte-for-byte:

```text
snap_drawing/experimental/tgfx/full/tests/media-data/pattern.png
snap_drawing/experimental/tgfx/full/app/fixtures/image.svg
apps/integration_test/src/valdi/integration_test_app/res/animation.json
snap_drawing/experimental/tgfx/full/tests/media-data/Montserrat-Regular.ttf
snap_drawing/experimental/tgfx/full/tests/media-data/Montserrat-LICENSE.txt
```

The current catalog compiler accepts PNG/WebP and TTF, not SVG/Lottie.
Consequently the compile script stages the original PNG and font for the
catalog and emits original PNG/SVG/Lottie bytes into `Fixtures.ts`. Resource
compiler image conversion is expected for catalog PNGs; original source bytes
remain staged and hashed, and the PNG byte-asset path bypasses that conversion.

## Schema 1 reports and pass criteria

Every event includes `schema: 1`, `metric`, and the exact `scope` string stated
above. The report sequence is:

- `kind: "started"`, `status: "RUNNING"`, `completed: false`, `suiteIds`, `plan`,
  `provenance`. Emitted once, before setup; the executing Hermes contract is
  then verified through `HermesInternal.getRuntimeProperties()`.
- Four `kind: "scene"` events in `suiteIds` order, with zero-based `index`,
  `status`, `completed`, `suiteIds`, and `result`.
- `kind: "finished"`, `status: "PASS" | "FAIL"`, `completed`, `suiteIds`, `plan`,
  `engine`, `provenance`, `scenes`, and optional `error`. `engine` contains the
  actual Hermes properties if its verification succeeded.

Each `result` includes `id`, `workload`, dimensions, planned `warmupCount=30`
and `measuredCount=300`, actual `warmupDurationsMs` and `durationsMs`,
`warmupPhaseDurationsMs` and `phaseDurationsMs` objects with `processFrameMs`,
`drawMs`, `rasterMs` arrays, setup `preparation`, asset evidence, first/last
canaries, `outputRelationshipPassed`, status and completion. On an early
failure arrays may be partial: their lengths are the actual recorded counts.
There are no fabricated zero placeholders for unperformed iterations.

`summary` exists only if all full-length timing arrays are valid. Its fields
are `totalMs`, `meanMs`, `minMs`, `p50Ms`, `p95Ms`, `maxMs`, and
`rendersPerSecond = 300*1000 / totalMs`. Percentiles use nearest rank.
`rendersPerSecond` is unpaced API throughput and must never be displayed as
screen FPS. Raw arrays are retained for analysis; no per-frame report is sent.

First/last canaries inspect actual bitmap bytes after raster completion.
They include an FNV-1a 32-bit hash of RGBA bytes (a canary, not cryptographic
equivalence), byte count, opaque/nonwhite/glyph coverage, and scene-specific
pixel samples. Vector color/coverage, dark text coverage, PNG/catalog/SVG
colors and the Lottie center/exterior are checked. All outputs must be the full
RGBA size, opaque, have nonempty scene content and the expected white background.
Static scenes require equal first/last hashes; Lottie requires different hashes.
Asset scenes also require native tracked assets and successful load callbacks,
with no load errors. These checks detect blank/static/missing outputs; they do
not prove full cross-backend pixel equivalence. Parent image-difference or
separate GPU correctness fixtures can provide stronger equivalence evidence.

Scene `PASS` requires all 30/300 positive finite total timings, full-length
nonnegative finite phase timings, finite positive summary fields, both canaries,
the expected hash relationship, and no asset errors. A scene can be completed
yet fail correctness. Terminal `completed: true` means all four scenes completed
in order; terminal `PASS` additionally requires every scene to pass. Exceptions
or partial scenes produce `FAIL`. Missing/destroyed/stalled runs cannot be
accepted merely because a previous scene passed. Report callbacks should not
throw; a host logging failure is a host failure.

## Parent measurement responsibilities

Build both native backends with matching Release/optimization/strip settings
and the exact shared module package. The parent's Android release invocation
uses `-c opt --snap_flavor=production --strip=always`; record actual command,
artifact SHA, ABI, linked backend and runtime identity with results. Apply
equivalent Release discipline on iOS, while recording the actual iOS settings.
This source does not certify those builds.

Measure real screen FPS separately with a frame-paced onscreen fixture. Measure
power only on actual mobile hardware with an explicit method, thermal/battery
conditions and run window. Emulator process activity is not device energy.
Compare binary/package sizes from matching native artifacts, separately from
the shared JS module/resource sizes; module compile success supplies no native
size or power evidence. Preserve GPU-vs-GPU fixture results separately from this
managed CPU-raster/GPU-readback comparison.
